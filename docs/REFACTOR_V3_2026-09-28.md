# Architecture refactor V3 — planning coordinator split

V3 continues the behavior-preserving restructure after the domain move and V2 guardrails.

## Why this pass

`app/Game.ts` still owned too much temporary placement state and detailed road/field planning behavior. That made even small road or field changes require reading a thousand-line application coordinator.

## New ownership

- `app/PlanningState.ts` — one transient state object for building placement, road drafting, field drafting, snapping and drag state.
- `app/PlanningOperations.ts` — road/field state mutations and finalization.
- `app/PlanningPresentation.ts` — placement validation projection, ghost rendering and contextual preview text.
- `app/Game.ts` — browser event orchestration, high-level commands, simulation loop and selection.

## Cleanup / bug fixes

Repeated manual planner resets were replaced by `clearPlanningDrafts` / `resetPlanningForImport`. This also clears field draft state when camera/cinematic mode exits placement, preventing invisible stale field corners from surviving mode changes.

The extraction exposed two accidental `roadCurveLabel` qualifications during the mechanical state move; both were corrected before merge and TypeScript verification.

## Result

Compared with the V2 main branch, `Game.ts` is reduced from about 1,190 lines to under 1,000 while road/field rules and ghost presentation now have direct navigation targets.

## Follow-up

The constructor still contains browser pointer and keyboard wiring. Split this next only as cohesive controllers; do not scatter individual event handlers into utility functions.

The action switch can later be divided into command domains after the active HUD redesign has landed, because UI action names are part of that integration surface.
